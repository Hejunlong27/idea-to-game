# 数值平衡调优

数值不能靠「感觉差不多」。但也不能靠「跑 100 局算胜率」——那是把不确定性强加给一个确定性的系统。

## 为什么不用胜率

塔防、模拟器这类玩法是**确定性**的：同一配置 + 同一操作序列 = 同一结果。

跑 10 局得到的是同一个样本。报「新手胜率 80%」是自欺欺人——那个 80% 不存在，只有 0% 或 100%。

真正有信息量的是两件事：

1. **不同水平的玩家能不能过**（二值）
2. **过了之后还剩多少余量**（连续）

「新手剩 6/10 血勉强过」和「新手剩 10/10 血轻松过」是两种完全不同的难度，而胜负字段看不出来。

## 两个策略代表两种水平

| 策略 | 行为 | 像谁 |
|---|---|---|
| `novice` | 按阅读顺序建塔（左上优先）、不评估覆盖、钱不够两座塔就攒着 | 第一次玩的人 |
| `expert` | 逐个候选格算「射程内覆盖多少路径格」，选覆盖最多的 | 算过的人 |

差异是**真实的决策差异**，不是给 novice 加延迟或降属性作弊。这一点很重要：
如果靠削弱 novice 来制造差距，测出来的就不是难度，而是惩罚。

## 甜点判定

| 新手 | 老手 | 判定 | 含义 |
|---|---|---|---|
| ✗ | ✗ | `TOO_HARD` | 太难 |
| ✗ | ✓ | `EXPERT_ONLY` | 只有算过的人才过得了 |
| ✓ | ✓（余量 ≥90% 且 <25s） | `TOO_EASY` | 太简单 |
| ✓（余量 30–90%） | ✓ | `SWEET_SPOT` | **甜点** |
| ✓（余量 <30%） | ✓ | `TIGHT` | 新手险过 |

推荐逻辑：在 `SWEET_SPOT` 里选「新手余量最接近 40%」的配置——有压力但不劝退。

## 用法

```bash
node scripts/balance_search.mjs                 # 按 balance-search.json 跑
node scripts/balance_search.mjs --only towerCostMul=1.0   # 收敛单参数
```

`balance-search.json`：

```json
{ "params": {
    "towerCostMul": [0.9, 1.2],
    "enemyHpMul":   [1.0, 1.3]
  },
  "strategies": ["novice", "expert"] }
```

笛卡尔积展开成 4 个配置 × 2 策略 = 8 局，每局约 1 分钟。

**控制搜索规模**：每多一个参数值就多 2 局。先粗扫（2×2），找到甜点区域后再细化。

## 输出（塔防实测）

```
towerCostMul  enemyHpMul    novice              expert              判定
0.9           1.0           ✓ 8/10血 30s        ✓ 10/10血 32s       SWEET_SPOT
0.9           1.3           ✗ 0/10血 40s        ✓ 10/10血 39s       EXPERT_ONLY
1.2           1.0           ✓ 5/10血 58s        ✓ 10/10血 38s       SWEET_SPOT
1.2           1.3           ✗ 0/10血 42s        ✓ 10/10血 45s       EXPERT_ONLY
```

这张表能直接读出两件事：

1. **血量倍率是难度主导**：1.0 → 1.3 直接把新手从「能过」打到「过不了」，而塔价 0.9 → 1.2 只是余量从 8 血降到 5 血。
2. **塔价影响的是节奏不是难度**：1.2 倍时新手要 58s（vs 30s），因为攒钱更久——这是「拖沓」不是「更难」。

所以调数值的分工是：**要调难度改血量倍率，要调节奏改价格倍率。**

## 推荐逻辑踩过的坑

第一版推荐只按「余量最接近 40%」选，选中了 `1.2/1.0`（剩 50% 血）。
但那个配置新手用了 **58 秒**——比 `0.9/1.0` 的 30 秒慢近一倍。

**「能过但拖沓」是体验变差，不是有压力。** 所以推荐必须加用时约束：
先筛掉用时超过最短 1.3 倍的配置，再挑余量最接近 50% 的。

修正后推荐 `0.9/1.0`，并明确打印「排除了 1 个能过但拖沓的配置」。

## `--reanalyze`

改判定逻辑后不必重跑 5 分钟，直接从 `balance-search.json` 重算结论：

```bash
node scripts/balance_search.mjs --reanalyze
```

## 局限

- **两个 bot 不等于真实玩家**。它们只代表「按规则出牌」的两种水平，不代表手感、注意力、疲劳。
- **只能测到「能不能过」**，测不到「好不好玩」。趣味性必须真人测。
- **单关单地图**。跨关卡难度曲线要分别跑。

所以这个工具的正确用法是**排除明显失衡的配置**，而不是「找出完美数值」。
