# 真人试玩协议

## 为什么必须真人玩

所有自动化测试都回答不了三个问题：

1. **第一次玩的人知不知道该干什么**（bot 天生知道）
2. **卡住的时候是什么感受**（bot 不会卡住）
3. **玩完想不想再来**（bot 没有意愿）

这三个才是「好不好玩」的全部。所以真人试玩不是「补充验证」，是**唯一能验证趣味性的手段**。

## 启动

```bash
cd <项目>
npm run dev
# 浏览器打开 http://localhost:5173/?playtest=1
```

`?playtest=1` 开启遥测。不带这个参数时零记录、零开销，是正常游玩模式。

## 试玩规则（重要）

1. **不要先看代码**。第一印象才是有效数据。
2. **按第一直觉玩**，不要为了「测试」而刻意找 bug。
3. **卡住就卡住**，不要硬想。你的犹豫本身就是最有价值的信号。
4. 玩完一局就够。**结束时游戏会自动下载 `playtest-<时间戳>.json`**。

## 玩完回答五个问题

不用长篇，一句话就行：

| # | 问题 | 想验证什么 |
|---|---|---|
| 1 | 进来第一眼，你知道要做什么吗？如果不知道，缺什么？ | 引导有效性 |
| 2 | 哪个瞬间最困惑/最无聊？ | 体验断点 |
| 3 | 哪一刻最有成就感？ | 爽点在哪 |
| 4 | 如果这是商店里的游戏，你会下载吗？为什么？ | 留存意愿 |
| 5 | 哪里最想改？ | 优先级 |

## 分析

```bash
node scripts/playtest_report.mjs --dir ~/Downloads
```

输出三档：

| 级别 | 含义 |
|---|---|
| `FAIL` | 完全没理解玩法（整局零建塔） |
| `WARN` | 有明确的体验问题（首次建塔太慢 / 长时间空闲） |
| `INFO` | 参考信息（崩盘波次、无效点击比例） |

## 三个核心指标的判读

| 指标 | 健康值 | 越界说明 |
|---|---|---|
| 首次建塔延迟 | < 10s | 太长 = 引导没让人看懂该点哪 |
| 最长空闲 | < 12s | 太长 = 卡住了或在找东西 |
| 崩盘波次 | ≥ 倒数第二波 | 太早 = 前中期难度陡增 |

**注意「首次建塔延迟」这个指标的特殊性**：它几乎只受引导影响，跟数值平衡无关。
如果这个数很大，改数值是白费力气，要改的是引导。

## 判读的边界

- **遥测记录行为，不记录感受**。「觉得好不好玩」必须问人，数据答不了。
- **单次试玩不是统计**。一个人卡住可能是他个人的问题；三个人都卡在同一处才是设计问题。
- **不要用试玩数据做「通过/不通过」的门禁**。它是用来**发现问题的**，不是用来判死刑的。

## 与 bot 试玩的分工

| 工具 | 回答 |
|---|---|
| `playtest.mjs`（bot 策略） | 能不能过、会不会卡死、有没有异常 |
| `balance_search.mjs`（双策略） | 难度对新手的容错窗口有多大 |
| **真人试玩 + 遥测** | **人会不会玩、玩得爽不爽、想不想再来** |

三者不可互相替代。bot 跑一万次也测不出「第一眼不知道点哪」。
